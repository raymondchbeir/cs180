A.1 / SHOOT THE PICTURES

Taking the photographs

I started by taking three sets of images with three pictures per set and tried to keep the camera in roughly the same position while rotating it between shots, this way there is enough overlap between the photos for me to match the same objects or corners and later align them using a homography.

My image sets

The original images were pretty large and my first inverse warping implementation had nested loops going over every pixel so it was taking a long time to run, I downsampled the photographs to a maximum width of 800 pixels while keeping their original aspect ratio, then I selected the correspondences again using the resized images because their pixel coordinates changed.

A.2 / RECOVER HOMOGRAPHIES

Finding the transformations

After taking the pictures I needed a way to map the same points from one image into another, so I selected points that were visible in both photographs using the previous student's correspondence tool and then set up my own system of equations for the homography, I used the middle image of every set as the reference since it makes the panorama easier to combine later.

Solving for H

A homography is a 3 by 3 matrix and because its scale does not matter we can fix the bottom right element to 1, leaving eight unknowns, each pair of corresponding points gives us two equations and I put these into the matrix A and the vector b then solved using least squares with NumPy.

p' ∼ H p   ·   A h = b   ·   h = np.linalg.lstsq(A, b, rcond=None)[0]For each match (x,y) → (x',y'), the rows in A are [x, y, 1, 0, 0, 0, −xx', −yx'] and [0, 0, 0, x, y, 1, −xy', −yy'] while b contains x' and y'.

I originally tried only four points for some of the pairs and even though that gave a solution the warped corners were sometimes extremely distorted, especially on the 4 to 5 pair, so I went back and picked more points across the overlap and the results were much better after that.

A.3 / WARP THE IMAGES

Inverse warping and interpolation

Once I had the homographies I needed to actually create the warped images, I first transformed the corners of each image using H so I could find the bounds of the output and then for every pixel of that new output I applied the inverse homography to figure out where it should sample the color in the original image.

Nearest neighbor vs bilinear

I implemented both methods myself, for nearest neighbor I rounded the source coordinates and copied the closest pixel which is simple but can look more blocky, for bilinear I used the four surrounding pixels and multiplied each color by its fractional distance weight so the result is smoother although it takes more work per pixel.

source ∼ H⁻¹ [x, y, 1]ᵀNearest neighbor rounds (x, y), bilinear uses floor(x), floor(y), and the fractional parts dx and dy to average the four surrounding colors.

Nearest neighbor needs only one source pixel per output pixel so it is the cheaper method, bilinear needs four pixels and a weighted sum which costs more but generally gives less jagged edges, and in my implementation both methods also spend time in the Python loops because I am processing each output pixel separately.

A.4 / BLEND IMAGES INTO A MOSAIC

Building the panoramas

For the last part I wanted to put all three photographs from each set into the same image, I left the middle one unchanged and mapped the other two into its coordinate system, then I calculated one big bounding box using the transformed corners of all three images so the final output would have enough room for everything.

Weighted averaging

At first I just copied each pixel into the output but the problem was that the next image would overwrite the previous one wherever they overlapped, so instead I made one array to add the weighted RGB colors and a second array to store the sum of weights, the weight I used was one plus the minimum distance from the sampled pixel to any of the four edges of its original image.

w = 1 + min(x, W − 1 − x, y, H − 1 − y)For overlapping pixels the final RGB value is sum(wᵢ · Iᵢ) / sum(wᵢ), so pixels farther from an image edge contribute more.

This lets the pixels near the interior of each photograph have more influence while the ones near the edges contribute less, it also means I only divide by the weight sum when at least one image actually covers the output pixel, so the rest of the canvas stays empty instead of accidentally treating a black pixel as missing data.

B.1 / HARRIS CORNER DETECTION

Finding corners automatically

For Part B I wanted to get rid of the part where I had to click on matching points myself, so first I needed to find interesting points in each picture and then choose which ones to keep.

Harris and ANMS

I used the provided Harris corner code for this part, it turns the image into grayscale and finds spots where the intensity changes a lot in both directions, the function gives me a response value for each pixel and the coordinates of the corners, but there can be a lot of corners all sitting very close to each other.

To fix that I implemented adaptive non maximal suppression or ANMS, I used the squared distance function to compare every pair of points and for each corner I found the closest point that was sufficiently stronger than it, using the condition f(i) < 0.9 f(j), then I put the radii into a heap and kept the 20 percent with the largest radii. This spreads the points across the picture instead of just picking the highest Harris scores in one area.

r(i) = distance to nearest j with f(i) < 0.9 f(j)The biggest radii are kept. I used the squared distances directly since they give the same ordering.

B.2 / FEATURE DESCRIPTORS

Describing each corner

After getting the corners I still needed a way to tell if a point in one image is the same point in another one, so I made a small descriptor for the pixels around each selected corner.

40 by 40 to 8 by 8

For every selected corner I took a 40 by 40 grayscale patch centered around that point, then I resized it to 8 by 8 with anti aliasing, the idea is that I want to keep the overall appearance of the area without being too sensitive to tiny changes in individual pixels.

After that I subtracted the mean of the patch and divided by its standard deviation so changes in brightness and contrast would not affect matching as much, and finally I flattened the 8 by 8 patch into 64 values. I also kept the original corner coordinates so I could find their positions again in the matching step.

40 × 40 patch → 8 × 8 patch → normalize → 64 numbersOne descriptor for each selected corner. No rotation correction in this part.
B.3 / FEATURE MATCHING

Matching points between images

Now that every corner has a descriptor I can compare points between two pictures without manually clicking them, I used the same image pairs as Part A so I can use the results to stitch the same three panoramas.

Nearest neighbor ratio

I compared each descriptor from the first image with all descriptors in the second image using squared Euclidean distances, then for each row I found the closest match and the second closest match, if the first one is much better than the second one then the match is probably more reliable.

I used the simple Lowe ratio test that the assignment asks for, the ratio is the actual nearest distance divided by the second nearest distance, and I kept matches when this was below 0.7, I used the square root of the squared distances before calculating that ratio.

ratio = distance(1-NN) / distance(2-NN) < 0.7Only the closest descriptor gets stored as a candidate match. The second one is just used for the test.

I got 421 matches for images 1 to 2, 395 for 3 to 2, 463 for 4 to 5, 345 for 6 to 5, 376 for 7 to 8 and 420 for 9 to 8. Some of the lines are wrong because similar areas can still have similar descriptors, so the next part will get rid of those bad matches using RANSAC.

B.4 / RANSAC AND AUTOMATIC MOSAICS

Stitching without manual matches

For the final part I wanted to use the matched points to find the homographies automatically and then reuse my stitching code from Part A without having to select the coordinates myself.

My four point RANSAC

I already had my computeH function from Part A so I reused it here, I randomly picked four of the feature matches and used those four pairs to calculate a homography, then I applied that homography to all the matched points and checked how far each predicted location was from the location of its match in the second picture.

If the error was below 3 pixels I counted the point as an inlier, I repeated this 2000 times and kept the group that had the most inliers, then I calculated a new homography using all the inliers from that best group instead of just the four random pairs.

4 random pairs → compute H → test every pair → count errors below 3 px → repeat2,000 trials for each image pair, then compute the final H from the best inliers.

Manual vs automatic results

For each group of three images I used the middle one as the reference, and with the new homographies I ran my original A.4 code which finds the shared bounding box, does inverse warping, and uses weighted averaging where the images overlap.
